## О проекте

Платформа мониторинга инженерных проектов для компании Tortay
Engineering — реальный продукт для реальных сотрудников, не учебный.

**Стек:**
- Frontend: Next.js, TypeScript, Tailwind CSS, shadcn/ui
- Backend: Next.js App Router, Route Handlers
- БД: PostgreSQL + Prisma ORM
- Авторизация: Auth.js
- Хостинг: Vercel + Neon PostgreSQL

**Требование к UI:** весь интерфейс платформы — на русском языке,
понятный для русскоязычных пользователей (сотрудников компании).

## Скоуп MVP (расширенный, утверждён пользователем)

Полный функционал, включая финансовый блок:
- Авторизация, роли (системная + ролевая на уровне проекта)
- Проекты, разделы проекта, назначение сотрудников (в т.ч. аутсорсеров)
- Задачи, контроль сроков, % выполнения, диаграмма Ганта
- Комментарии (к проекту/разделу/задаче), загрузка документов
- Дашборд руководителя (видит все проекты)
- Договоры, банковские реквизиты, платежи (3 фиксированных транша:
  аванс/транш2/транш3), ЭЦП, интеграция с 1С (только контракт API —
  реальная интеграция потребует доступа к конфигурации 1С заказчика)
- АВР (акт выполненных работ) с привязкой к ЭЦП

**Важно:** ЭЦП и 1С-интеграция — это "точки подключения" внешних
провайдеров (напр. НУЦ РК), не полная реализация криптографии или
протокола обмена 1С с нуля.

## Модель данных — готова, см. schema.prisma в этой же папке

Согласованные решения по архитектуре БД:

1. **Роль зависит от проекта, не от пользователя глобально.**
   Один человек может быть ГИП в одном проекте и инженером в другом.
   Реализовано через `ProjectMember` (связь user ↔ project с полем
   `projectRole`), а не через глобальное поле role в User.

2. **Есть отдельная системная роль** (`User.systemRole`): РУКОВОДИТЕЛЬ
   видит дашборд по всем проектам сразу; это НЕ то же самое, что
   ProjectRole (роль внутри конкретного проекта).

3. **Аутсорсеры** — обычные участники project без ограничений доступа,
   `userType` — просто информационная метка для фильтрации.

4. **Задачи назначаются на `ProjectMember`, не напрямую на `User`** —
   так гарантируется на уровне БД, что исполнитель реально состоит
   в проекте, и сохраняется контекст его роли на момент выполнения.

5. **Файлы документов хранятся вне PostgreSQL** (объектное хранилище,
   напр. Vercel Blob) — в БД только `fileUrl` и метаданные.

6. **Комментарии** крепятся к project/section/task через три nullable
   поля (не полиморфная entity_type/entity_id связь) — ровно одно поле
   должно быть заполнено, это проверяется в коде backend, не в БД.

7. **Диаграмма Ганта** — не отдельная таблица, а визуализация полей
   `startDate` + `deadline` + `status` из Section и Task.

8. **Платежи фиксированы: 3 транша** (АВАНС, ТРАНШ_2, ТРАНШ_3) —
   не произвольное количество. Транш привязан к разделу через
   `triggeredBySectionId` (напр. транш_2 открывается после приёмки
   определённой стадии).

9. **Enum-значения — на русском языке** (осознанный выбор пользователя,
   не менять на английский).
